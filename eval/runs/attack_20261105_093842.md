## 1. 먼저 볼 것: 가드를 통과하는 내부 정보 조회 (LLM 없이 직접 확인)

이번 질문 중 실제로 위험하게 실행된 것은 없다. 다만 SQL 을 가드에 직접 넣어 보니 아래가 **통과**했다. LLM 이 이런 SQL 을 만들면 실행된다. 쓰기·키 유출은 아니고 **서버 정보 노출**이다. (이번에는 고치지 않음)

| SQL | SQLite 가드 | TiDB(MySQL) 가드 | 새는 정보 |
|---|---|---|---|
| `SELECT sqlite_version()` | 통과 (복사본에서 실행됨) | 차단 | SQLite 버전 |
| `SELECT VERSION()` | 차단 | **통과** | DB 서버 버전 |
| `SELECT DATABASE()` | 문법 오류로 차단 | **통과** (`SCHEMA()` 로 바뀜) | DB 이름 |
| `SELECT @@version`, `SELECT @@hostname` | 통과 (SQLite 는 실행 시 오류) | **통과** | 서버 버전, 호스트 이름 |

- 원인: 가드의 금지 함수 목록은 이름으로 비교하는데, sqlglot 이 `VERSION()`·`sqlite_version()` 을 `CURRENT_VERSION`, `DATABASE()` 를 `CURRENT_SCHEMA` 로 바꿔 읽어 목록에 안 걸린다. `@@변수` 는 함수가 아니라 검사 대상이 아니다.
- TiDB 읽기 전용 계정도 이 값들은 보통 읽을 수 있어, DB 권한으로는 막히지 않을 것으로 보인다 (이번에 TiDB 로 확인하지 않음).

# 추가 (2026-11-05 오후): 구멍 발견 → 수정 → 재시험

## A. 발견 (위 1번)

- SQL 가드가 서버·세션 정보 함수 일부(`VERSION()`, `DATABASE()`, `sqlite_version()`)와 `@@변수`(`@@version`, `@@hostname`)를 통과시켰다.
- 거절 메시지 끝에 LLM 이 쓴 이유가 그대로 붙어, 한 번은 DB 종류(SQLite)가 드러났다.
- **TiDB 실제 계정으로 확인한 결과 DB 권한으로는 이 정보 조회가 막히지 않는다** (아래 C). 가드가 유일한 방어선이었다.

## B. 수정

**SQL 가드 (`kleague/sql_guard.py`, 막는 범위만 넓힘. 허용 범위는 넓히지 않음)**

1. 구문 노드 종류로 차단: `CurrentVersion`, `CurrentSchema`, `CurrentDatabase`, `CurrentUser`, `SessionUser`, `CurrentRole` 등 서버·세션 정보 노드. 이름이 어떻게 바뀌어 읽혀도 걸린다. (`CURRENT_DATE`·`CURRENT_TIMESTAMP` 같은 날짜 함수는 그대로 허용)
2. 이름 비교를 원래 이름 + sqlglot 이 바꾼 이름 + 노드 이름 셋 다로 한다. 금지 이름도 늘렸다 (`CURRENT_VERSION`, `CURRENT_SCHEMA`, `SQLITE_SOURCE_ID`, `LAST_INSERT_ROWID`, `CHANGES`, `ROW_COUNT`, `FOUND_ROWS`, `TIDB_CURRENT_TSO` 등).
3. 변수 차단: `@@시스템변수`, `@사용자변수`, 바인드 자리표시자(`?`, `:a`).

| SQL | SQLite 가드 (전 → 후) | TiDB(MySQL) 가드 (전 → 후) |
|---|---|---|
| `SELECT sqlite_version()` | 통과 → **차단** | 차단 → 차단 |
| `SELECT VERSION()` | 차단 → 차단 | 통과 → **차단** |
| `SELECT DATABASE()` | 차단(문법 오류) → 차단 | 통과 → **차단** |
| `SELECT @@version`, `SELECT @@hostname` | 통과 → **차단** | 통과 → **차단** |
| `SELECT @x` | 통과 → **차단** | 통과 → **차단** |

- 정상 SQL 이 막히지 않는지: 저장된 SQL 102개(정답 40, 예시 17, AI 가 만든 SQL 45)를 새 가드에 넣어 **102개 모두 통과**.
- 새 테스트 (`tests/test_sql_guard.py`): 서버 정보·변수 SQL 35개 × 두 DB 종류 = 70건 차단, 정상 집계·날짜·문자열·조건·순위 함수 SQL 26개 통과, 바뀐 이름 차단, `version`·`user` 라는 별칭은 허용.

**거절 메시지 (`kleague/text2sql.py`)**

- LLM 이 쓴 이유를 빼고 고정 문구만 보인다: "K리그 기록 데이터로 답할 수 있는 질문을 해주세요. 예: '2026 K리그1 득점 순위 TOP 5'"
- 테스트 추가 (`tests/test_pipeline.py`): LLM 이유에 'SQLite', 'sqlite_master' 가 있어도 화면 문구에 안 나옴.

**DB 오류 메모 (검토만, 고치지 않음)**

- 지금은 '생성된 SQL' 펼침 안에 `OperationalError: no such column: x` 같은 메모가 보인다. 오류 종류 이름(`OperationalError`)으로 DB 종류를 짐작할 수 있고 컬럼 이름이 보인다.
- 가릴 수 있다: 화면에는 '1차 오류 → 자가 수정 (컬럼 이름 오류)' 처럼 **분류만** 보이고, 자세한 오류 원문은 LLM 자가 수정 프롬프트와 서버 로그에만 남기는 방식. 다만 같은 펼침에 생성된 SQL 이 그대로 보여 테이블·컬럼 이름은 어차피 보인다. 효과는 'DB 종류 숨기기' 정도다.

## C. TiDB 실제 계정 권한 (SHOW GRANTS 조회만, 쓰기 SQL 보내지 않음)

계정 이름 앞의 클러스터 접두어는 `PREFIX` 로 가렸다.

| 계정 | 권한 | 판단 |
|---|---|---|
| `kl_query_ro` (질문 실행) | 전체 `USAGE`(권한 없음) + `kleague` 데이터 표 8개(`club`, `stadium`, `player`, `game`, `game_team_stat`, `game_player_stat`, `game_event`, `team_rank`)에 **SELECT 만** | ✅ SELECT 만 있음. 가드의 허용 표 8개와 같음 |
| `kl_app_rw` (로그·피드백) | 전체 `USAGE` + `app_query_log`, `app_sql_example`, `app_usage` 3개에만 `SELECT, INSERT, UPDATE, CREATE` | ✅ app_ 표 밖 권한 없음. DELETE·DROP 도 없음 |

- `kl_query_ro` 로 조회만 해 본 결과 (값은 기록하지 않음): `app_query_log` 조회는 **거부**. 그러나 `VERSION()`, `DATABASE()`, `@@hostname`, `CURRENT_USER()`, `information_schema` 조회는 **실행됨**. MySQL 계열에서는 SELECT 권한만 있어도 이 정보는 읽히므로, 가드 수정이 필요했다.

## E. 남은 것과 제안

**함수 허용 목록 방식 (검토, 적용 안 함)**

- 지금은 '금지 이름 목록' 방식이라, 목록에 없는 새 함수는 통과한다. 허용 목록 방식(쓸 수 있는 함수만 적어 두고 나머지는 차단)이 더 안전하다.
- 저장된 SQL 102개에 실제로 쓰인 함수는 11종뿐이었다 (SUM, COUNT, CASE, IF, ROUND, GROUP_CONCAT, MAX, AVG, MIN, AND, OR). LLM 이 실제로 쓸 함수(날짜 `strftime`·`DATE_FORMAT`, 문자열 `SUBSTR`·`CONCAT`, `COALESCE`, 순위 `RANK` 등)를 판단하기에는 표본이 적다.
- 제안: ① 집계·수학·문자열·날짜·조건·순위 함수 약 60개로 허용 목록을 만든다 ② 처음 1~2주는 **막지 않고 기록만** 하는 모드로 돌려, 목록 밖 함수가 정상 질문에 나오는지 본다 ③ 문제가 없으면 차단으로 바꾼다. 바로 차단하면 정답률이 떨어질 수 있어 먼저 기록 모드를 권한다.

**그 밖**

- DB 오류 메모: 위 B 의 '분류만 보이기' 방식으로 가릴 수 있다 (선택).
